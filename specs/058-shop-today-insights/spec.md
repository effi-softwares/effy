# Feature Specification: Shop Console — Today & Insights

**Feature Branch**: `058-shop-today-insights`

**Created**: 2026-09-10

**Status**: Draft

**Input**: User description: "Implement the Today (operations dashboard) and Insights (analytics) screens in the shop web console, per the Claude Design mockup `Effy Shop Console.dc.html` (project `951bb710`), screens `Today` and `Insights`. Part A specifies the UI exactly; Part B requires researching how production e-commerce consoles serve pre-aggregated analytics and realtime order feeds (with a hard cost requirement) and recording it in `docs/insights-architecture.md` before implementation; an Insights read served from pre-aggregated rollups, cached per shop/range/timezone; a realtime Live orders feed with backfill on (re)connect and a polling fallback; operational numbers from live order state, analytics numbers only from rollups."

## Source Design — What Was Imported

The mockup was read in full through `DesignSync` (it is not in the repo). It is the same **generic
e-commerce console built for a fictional Swedish home-goods brand** that 057 imported: SEK, "incl. VAT",
Stockholm, `orders@effy.shop`, simulated arrivals generated by a timer, and seeded names and products.
Its two screens:

- **Today** — header (title, weekday · date · city subtitle, `Quick actions` / `Team activity` /
  `Print pick lists`), a **Needs attention** card and a **Live orders** card side by side, and a slim
  **Today at a glance** card of four figures. Two right-side sheets (`Quick actions`, `Team activity`)
  and two dialogs (`Message a customer`, `New discount code`).
- **Insights** — header (range title, window subtitle, `Today / 7 days / 30 days` segmented control,
  `Export CSV`), a five-cell primary metric strip, a five-cell clickable secondary strip, twin bar
  charts (`Revenue`, `Order volume`) and a **Top products** list.

This slice **replaces** 057's dashboard (User Story 1, FR-006…FR-008) with Today and adds Insights as a
new console destination. Everything 057 settled about Effy's model carries over unchanged, and the
mockup is mapped onto it the way 057 A3 §1 mapped the order console:

| Mockup | Effy | Why |
|---|---|---|
| SEK, `kr`, "SEK incl. VAT" | AUD, `$`, no tax claim | Effy is Australian; per-item GST is unmodelled, so "incl. GST" is false for a mixed grocery basket (052 R13) |
| Stockholm, shop timezone | The shop's operating timezone, Melbourne by default | Shops carry no address yet (049 R13); delivery is already judged in Melbourne wall-clock (047) |
| Channel ("Online store") | Delivery method (Same-day / Standard) | Effy has one sales channel; 057 A3 §1.6 already made this mapping |
| "Refund waiting for approval" | A refund the platform proposes for this shop's portion (unavailable lines) | Refund proposals are derived (055); a shop manager issues them (057 FR-014) |
| "Below reorder point", "days of cover" | At or below the low-stock threshold; cover derived from recorded sales | 057 A2 refused the reorder point; the threshold is the real equivalent (054) |
| "17 views today" | Real demand for the product (units ordered or short) | The platform does not record product views for a shop |
| `New order`, `Discount code`, `Message a customer` | Not built | FR-011 |
| `Conversion rate`, `New customers`, `Returns open` | `Can't supply`, `Cancelled`, `Ready for pickup` | FR-034 |
| Revenue = order totals | Revenue = the shop's goods value | FR-032 |
| Simulated arrivals, "still coming in" rows | None — every row is a persisted order | A shop learns of an order only after the platform has stored it (019 fan-out) |
| Amber `--warning`, green-as-text, `--success-soft` fills | Monochrome emphasis; the success colour only as a non-text dot | Colour law (constitution v1.13.0); 057 refused the same tokens three times |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - The operator opens the console and sees what needs doing right now (Priority: P1)

A shop operator opens the console at the start of a shift. The Today screen tells them, without any
date range or chart, what is waiting: orders to pick (with the unit count and how long the oldest has
waited), products out of stock or running low, and refunds the platform is proposing for their shop.
Each item has one verb-specific button that takes them to the screen that resolves it. Items they clear
drop off by themselves.

**Why this priority**: This is the screen the operator lands on every time. It replaces a dashboard
that already exists, so it must be at least as useful as that one on day one.

**Independent Test**: Seed a shop with two orders awaiting pick (five units), one tracked product at 0
on hand and one below its threshold. Open Today and confirm the four figures that describe the pick
backlog agree everywhere, that each button opens the right screen, and that picking one order changes
every one of those figures together.

**Acceptance Scenarios**:

1. **Given** three orders awaiting pick holding eleven units, **When** the operator opens Today, **Then**
   the Needs attention card shows "3 orders awaiting pick" / "11 units to pack · oldest {age}", the
   Awaiting pick glance cell shows 3 with "11 units to pack", and the open-items badge counts that item.
2. **Given** that state, **When** a teammate starts picking one of those orders, **Then** within the
   freshness bound (SC-002) the title, the unit figure, the badge and the glance cell all change together,
   and never disagree with each other at any moment.
3. **Given** a tracked product with 0 on hand, **When** the operator presses `Restock`, **Then** that
   product's detail screen opens.
4. **Given** nothing is waiting, out of stock or proposed, **When** the operator opens Today, **Then**
   the Needs attention card shows a calm, explicit steady state rather than an empty list or a zero badge.
5. **Given** today is a Thursday and the shop operates in Melbourne, **When** Today loads, **Then** the
   subtitle reads "Thursday 10 September · Melbourne", derived from the clock and the shop's timezone.

---

### User Story 2 - New orders appear on Today as they are paid (Priority: P1)

While Today is open, a customer pays for an order that includes this shop's products. It appears at
the top of Live orders with a `New` marker, its relative time ages on its own ("Just now" → "1 min
ago" → "3 min ago"), and the pick backlog grows to match. If the connection drops and comes back, the
list is rebuilt from what the platform has stored rather than trusted to have missed nothing.

**Why this priority**: The operator's reason to keep the console open is to see work arrive; a
feed that silently stalls is worse than none, because it looks current.

**Independent Test**: With Today open, complete a test checkout containing this shop's product. Confirm
the row appears within the freshness bound, that it opens that exact order's detail, that the `New`
marker disappears after a minute, and that cutting the network for two minutes and restoring it shows
every order paid in the gap.

**Acceptance Scenarios**:

1. **Given** Today is open, **When** an order containing this shop's items is paid, **Then** it appears
   as the first Live orders row within the freshness bound, with its order number, customer name, `New`
   marker, "Just now · {n} items · {delivery method}" and its total.
2. **Given** that row, **When** 60 seconds pass with no new data, **Then** the `New` marker is gone and the
   relative time has advanced, without a reload.
3. **Given** the live connection is lost while two orders are paid, **When** it returns, **Then** both
   orders appear in the correct order, with no duplicate row and no gap.
4. **Given** the live connection cannot be established at all, **When** the operator uses Today, **Then**
   the screen looks and behaves identically, updated by periodic refresh within the fallback bound.
5. **Given** any Live orders row, **When** the operator clicks it, **Then** the detail page of the order
   with exactly that order number opens.
6. **Given** an order paid for another shop only, **When** it is paid, **Then** it never appears on this
   shop's Today.

---

### User Story 3 - The operator reads how the shop is performing over a period (Priority: P2)

A shop manager opens Insights, chooses Today, 7 days or 30 days, and reads revenue, order count,
average order value, refunds and top products for that window, each with a stated comparison against
the previous equivalent window, plus two bar charts bucketed by hour, day or week. Every figure that
explains a problem drills through to the list behind it.

**Why this priority**: Valuable, but nothing breaks if it arrives after Today; the operator can
already see individual orders.

**Independent Test**: Seed a shop with known paid orders across the last 60 days. For each range,
confirm every figure matches a hand calculation over the seeded data in the shop's timezone, that every
delta states its basis, and that the page never waits on a calculation over raw orders.

**Acceptance Scenarios**:

1. **Given** the 7 days range, **When** Insights loads, **Then** the title reads "Last 7 days", the
   subtitle states the exact dates and "compared with the previous week" plus how recently the figures
   were updated, and every cell label restates the window ("Revenue, 7 days").
2. **Given** any range, **When** the operator switches it, **Then** every number, both charts and the Top
   products subtitle ("By revenue, last 7 days") change together; the chart bucket label never appears in
   the Top products subtitle.
3. **Given** the Today range, **When** the charts render, **Then** they show one bar per hour of the
   shop's trading day in the shop's timezone, the final (current) bucket emphasised.
4. **Given** the Awaiting pick and Unfulfilled units cells, **When** they are compared with Today,
   **Then** they show exactly the same values, whatever range is selected.
5. **Given** a refund settles for an order placed five days ago, **When** the figures are next refreshed,
   **Then** the 7-day and 30-day refund and revenue figures reflect it.
6. **Given** a secondary cell such as Low stock SKUs, **When** the operator clicks it, **Then** the list
   that explains the number opens, already filtered.
7. **Given** a brand-new shop with no orders, **When** Insights loads, **Then** it shows zeros and empty
   charts with a plain "no sales in this window" statement, never an error or a broken chart.

### User Story 4 - The operator starts any common task from one place (Priority: P2)

From Today, `Quick actions` opens a side sheet of every task the operator starts from the console,
grouped as Create, Fulfilment, and Customers and reporting, each row saying what it does. `Print pick
lists` prints one pick list per order awaiting pick.

**Why this priority**: Convenience over flows that mostly already exist elsewhere in the console.

**Independent Test**: Open the sheet, trigger each row, and confirm each ends where FR-010 says it does.

**Acceptance Scenarios**:

1. **Given** four orders awaiting pick, **When** the operator presses `Print pick lists` (header or sheet),
   **Then** four pick lists go to the print dialog and the toast reads "4 pick lists sent to printer".
2. **Given** no orders awaiting pick, **When** Today renders, **Then** `Print pick lists` is unavailable
   and says why, instead of printing nothing.
3. **Given** the sheet is open, **When** the operator chooses `Open the attention queue`, **Then** the sheet
   closes and the Orders list opens filtered to at-risk orders, oldest first.

---

### User Story 5 - The operator sees what the team has done (Priority: P3)

`Team activity` opens a side sheet listing everything recorded against this shop by its people, newest
first — picks, handovers, notes, tags, stock changes, refunds — each with who and when.

**Why this priority**: Accountability already exists per order; this only gathers it in one place.

**Independent Test**: Have two staff members pick, note and adjust stock; confirm the sheet lists each
action with the right person, in order, and nothing from any other shop.

**Acceptance Scenarios**:

1. **Given** staff activity today, **When** the sheet opens, **Then** each action appears once, newest
   first, as "{what happened}" over "{when} · {who}".
2. **Given** an action recorded without a person (made by the platform), **When** it is listed, **Then**
   it is attributed to Effy, never blank.

### Edge Cases

- **Timezone boundaries**: an order paid at 23:59 and another at 00:01 shop time fall in different "today"
  and different day buckets; daylight-saving changeover days have 23 or 25 hour buckets, not a
  mislabelled 24.
- **The comparison window has no data** (a shop open six days): the delta says there is nothing to
  compare against rather than showing "+∞%" or "+100%".
- **Refund or cancellation after the window closed**: it lands in the bucket of the day it was issued, so
  a reported past day does not change. What *can* change a past bucket is a correction to the refund
  itself (a submitted refund that later fails); the updated-at time says when figures were last
  recomputed.
- **Can't-supply / cancelled portions**: not counted as awaiting pick; whether they count toward revenue
  follows the refund, not the status alone.
- **Multi-shop orders**: each shop's figures include only its own portion, so the platform's shops'
  figures sum to the platform total without double counting.
- **A burst of orders** (more than five in a moment): Live orders shows the five most recent, newest first,
  and the pick backlog counts all of them.
- **A shop deactivated mid-session, or an operator deactivated**: the live feed stops and the console's
  existing fail-closed session handling takes over; no stale feed keeps running.
- **The tab is hidden for hours**: on return the screen refreshes rather than showing hours-old relative
  times as current.
- **Two browser tabs open**: both stay correct; neither disturbs the other.

## Requirements *(mandatory)*

### Functional Requirements

**Today — header and structure**

- **FR-001**: Today MUST replace the existing console dashboard as the console's landing screen, carrying
  the title `Today` and a subtitle of the weekday, date and the shop's timezone city, all derived.
- **FR-002**: Today MUST show no chart and no date range; every figure on it is scoped to the current day
  in the shop's timezone or to live state.
- **FR-003**: The header MUST carry, in order, `Quick actions`, `Team activity` and `Print pick lists`;
  the console header above it keeps the breadcrumb trail and does not repeat the title (057 A1).

**Today — Needs attention**

- **FR-004**: Needs attention MUST list, oldest-waiting first, one row per open item of these kinds, each
  with a tone marker, a title, a detail line and one action button:
  (a) orders awaiting pick — "{n} orders awaiting pick" / "{units} units to pack · oldest {age}", action
  `Pick` → the Orders list's Awaiting pick tab;
  (b) each tracked product with nothing on hand — "{product} out of stock" / on-hand plus one real demand
  fact, action `Restock` → that product's detail;
  (c) each tracked product at or below its low-stock threshold — "{product} below reorder point" /
  "{on hand} on hand, {d} days of cover" where cover is derivable from recorded sales and omitted where it
  is not, action `Review` → that product's detail;
  (d) each refund the platform proposes for this shop's portion of an order — "Refund waiting for approval"
  / "{order number} · {amount}", action `Approve` → that order's detail; shown only to operators who may
  issue refunds (057 FR-014).
- **FR-005**: The header MUST show "Oldest item waiting {age}" and a count badge of open items; the footer
  MUST read "Cleared items drop off automatically" with `Open queue →` to the at-risk Orders view.
- **FR-006**: The awaiting-pick order count, its unit figure, the badge's contribution, the glance cell and
  the Insights Awaiting pick / Unfulfilled units cells MUST all derive from ONE computed value, so they can
  never disagree on screen.
- **FR-007**: When there are no open items, the card MUST show an explicit steady state (057 FR-008).

**Today — Live orders**

- **FR-008**: Live orders MUST show this shop's five most recently paid orders, newest first: order number,
  customer name, a `New` marker only while the order is under 60 seconds old, a meta line
  "{relative time} · {n} items · {delivery method}", and the same total the Orders list shows for it. The
  newest arrival is visually emphasised. The footer reads "Showing the five most recent orders".
- **FR-009**: Relative times MUST age without new data ("Just now" → "1 min ago" → "3 min ago"), and every
  row MUST correspond to a stored order whose detail opens on click — the order with exactly the number
  the row displays. No placeholder, simulated or not-yet-stored row may exist.

**Today — Quick actions, dialogs, glance**

- **FR-010**: `Quick actions` MUST open a full-height right-side sheet titled `Quick actions` /
  "Everything you start from here." with no footer, whose rows carry a glyph tile, title, description and
  chevron, and behave as follows:
  - *Create* — `New product` closes the sheet and opens the new-product flow (the only Create row; see
    FR-011).
  - *Fulfilment* — `Print pick lists` ("{n} orders are waiting to be picked.") closes the sheet and prints;
    `Receive stock` closes it, toasts "Pick a product to receive stock into" and opens the Catalog;
    `Open the attention queue` closes it and opens the at-risk Orders view, oldest first, without
    re-adding the saved-views row 057 removed (FR-026).
  - *Customers and reporting* — `Export orders` closes it and exports the Orders list's CSV;
    `Open insights` closes it and opens Insights.
- **FR-011** *(clarified)*: The mockup's `New order`, `Discount code` and `Message a customer` rows, and the
  `Message a customer` and `New discount code` dialogs, MUST NOT be built — not shown, not disabled. A shop
  cannot create an order (057 FR-013); a discount code is platform-wide and would discount other shops'
  items (027); a customer's email is never shared with a shop (023 FR-018, 057 A3 §1.2). A source guard
  MUST fail naming the file if any of the three reappears, as 057's guards do for its refused controls.
- **FR-012**: `Team activity` MUST open a right-side sheet titled `Team activity` / "Everything the team
  has done, newest first." listing actions recorded against this shop, each "{what}" over
  "{when} · {who}", with platform-made actions attributed to Effy.
- **FR-013**: `Print pick lists` MUST produce one pick list per order awaiting pick — the same pick list the
  order detail prints — and toast "{n} pick lists sent to printer"; with none waiting it MUST be
  unavailable, saying why.
- **FR-014**: Today at a glance MUST show Revenue today, Orders today, Average order value and Awaiting pick
  ("{units} units to pack"), each with a comparison, and `Full insights →` to Insights. It MUST show the
  same values Insights shows for the Today range.

**Insights**

- **FR-015**: Insights MUST be a console destination with one range control (`Today` / `7 days` /
  `30 days`) that every figure on the page responds to, and an `Export CSV` of the figures shown.
- **FR-016**: The title MUST reflect the range (`Today` / `Last 7 days` / `Last 30 days`); the subtitle
  MUST state the exact window, its comparison basis, and how recently the figures were computed
  ("updated a moment ago").
- **FR-017**: The primary strip MUST show Revenue, Orders, Average order value, Awaiting pick and
  Unfulfilled units, labels and deltas restating the window ("Revenue, 7 days", "+9% vs previous week").
  The last two are live values identical to Today's (FR-006).
- **FR-018**: The secondary strip MUST show five clickable figures, each opening the already-filtered list
  that explains it: Refunds (→ orders with a refund in the window) and Low stock SKUs (→ the Catalog's
  low-stock view), plus the three of FR-034 — five cells in all, in the order Refunds, Can't supply, Low stock SKUs,
  Cancelled, Ready for pickup.
- **FR-019**: Twin charts `Revenue` ("{window} · AUD") and `Order volume` ("{window} · paid orders") MUST
  bucket by hour for Today, by day for 7 days and by week for 30 days, each headed by its total and trend,
  the final bucket emphasised.
- **FR-020**: Top products MUST list this shop's products by revenue in the window — thumbnail, name, SKU,
  a share bar with units, revenue — headed "By revenue, {today | last 7 days | last 30 days}" with
  `Catalog →`; each row opens that product's detail.

**Data rules (both screens)**

- **FR-021**: Every figure MUST cover only this shop's portion of each order; no figure may reveal other
  shops' portions, other shops' existence, or customer information a shop is not already shown (023
  FR-018).
- **FR-022**: Money MUST be shown in AUD on the basis of FR-032, with no claim about tax inclusion.
- **FR-023**: "Today", hour boundaries, day boundaries and week starts (Monday) MUST follow the shop's
  timezone, including on daylight-saving changeover days.
- **FR-024**: Every comparison MUST arrive with its figure and its stated basis (Today vs the same weekday
  last week; 7 days vs the previous 7; 30 days vs the previous 30). The console MUST NOT compute deltas.
- **FR-025**: Operational figures (awaiting pick, unfulfilled units, Needs attention, Live orders) MUST
  come from live order and stock state and be correct the moment it changes, within the freshness bound.
- **FR-026**: Analytics figures (everything on Insights except FR-017's last two, and Today's first three
  glance cells) MUST come from figures prepared ahead of the request; opening Insights MUST NOT trigger a
  calculation over the shop's raw order history.
- **FR-027**: A late correction — a refund, cancellation or can't-supply recorded after the fact — MUST
  reach every affected window and bucket within the analytics freshness bound (SC-004), by a documented
  path.
- **FR-028**: Live orders and the pick backlog MUST update from the platform's own payment confirmation
  (the verified, deduplicated event that already marks an order paid), rebuild from stored state on every
  (re)connection, fall back to periodic refresh when a live connection is unavailable with no visible
  difference, and apply each order exactly once in the right order.
- **FR-029**: Nothing on either screen may keep running after the operator leaves it: live connections,
  refresh timers and ageing ticks stop on exit.

**Research deliverable**

- **FR-030**: Before implementation, `docs/insights-architecture.md` MUST record the research Part B of the
  input asks for — how production commerce consoles serve pre-aggregated analytics and realtime order
  feeds, webhook reliability practice, and a cost comparison with concrete monthly figures at 10k and
  500k orders/month including free tiers — with cited sources, and MUST state the chosen arrangement and
  why, preferring the cheapest one that meets the requirements.

**Design law**

- **FR-031**: Both screens MUST follow the mockup's markup and copy (Part A verbatim, adapted only as the
  mapping table requires) within the colour law: no warning hue, the success colour never as text, deltas
  carried by sign and wording so colour is never the only signal.

- **FR-032** *(clarified)*: Revenue, average order value and Top products MUST measure the value of the
  goods this shop supplied on paid orders — excluding the delivery fee and any order-level discount, both
  of which Effy sets for the whole order — so that shops' figures sum to the platform's goods total with
  nothing counted twice. Refunds against the shop's goods are reported in the Refunds figure and
  reduce revenue **on the day the refund was issued**, not the day of the sale *(amended in /plan,
  research R4: this is how Shopify's sales reports date every reversal, and it means a reported past
  day never silently changes because of something that happened later)*.

**Access**

- **FR-033**: Both screens MUST be governed by the console's existing session and role gate: any active
  operator at an active shop may view them; actions a role cannot perform are not offered.

**Unsupported mockup figures**

- **FR-034** *(clarified)*: The mockup's `Conversion rate`, `New customers` and `Returns open` cells MUST
  NOT be built — a shop has no storefront of its own to convert, customer relationship data is withheld
  from shops (023 FR-018), and the platform has no returns model. Their three slots MUST carry, in the same
  layout and interaction:
  - `Can't supply` — this shop's portions declared can't-supply in the window, delta the units affected,
    → the Orders list's Can't supply tab;
  - `Cancelled` — this shop's portions cancelled in the window, → the Cancelled tab;
  - `Ready for pickup` — a live count of packages waiting for an Effy driver, from the same operational
    snapshot as FR-006, → the Ready tab.

### Key Entities

- **Shop operating timezone**: The timezone that defines a shop's "today", hours and weeks. Melbourne for
  every shop until shops carry their own location.
- **Operational snapshot**: The live state of a shop's work — orders awaiting pick and their units, out-of-
  stock and low-stock products, proposed refunds — computed from current order and stock records.
- **Live order entry**: One of the shop's most recently paid orders as the feed shows it, always a stored
  order.
- **Period figures**: Per-shop, per-bucket (hour/day/week) prepared figures — revenue, paid orders, units
  per product, refunds — from which each range and its comparison window are read; recomputed when a late
  correction touches a bucket.
- **Team activity entry**: One recorded action at the shop — who (a shop staff member or Effy), what, when —
  drawn from the records the platform already keeps (fulfilment events, notes, tags, stock movements,
  refunds).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Every number on both screens matches a hand calculation over seeded data in the shop's
  timezone, for all three ranges and on a daylight-saving changeover day.
- **SC-002**: A newly paid order appears on Today within 10 seconds for 95% of orders with a live
  connection, and within 30 seconds when relying on periodic refresh.
- **SC-003**: After a dropped connection of any length, 100% of orders paid in the gap appear once each,
  in order, with none duplicated.
- **SC-004**: Insights opens in under 1.5 seconds for 95% of loads at 500k orders/month, and its figures
  are never more than 5 minutes behind the records, late corrections included.
- **SC-005**: The pick backlog figures (count, units, badge, glance, both Insights cells) never disagree
  with each other, in any observed state.
- **SC-006**: No row, button or figure on either screen offers an action the platform cannot perform or a
  number the platform does not have (057 SC-006).
- **SC-007**: The monthly running cost added by this feature is stated in the research document at both
  volumes, and the chosen arrangement is the cheapest option there that meets SC-002…SC-004.
- **SC-008**: An operator can go from opening the console to acting on the most urgent item in two clicks
  or fewer (057 SC-002 retained).
- **SC-009**: Leaving either screen leaves no live connection or timer running.

## Assumptions

- **Shop timezone**: shops carry no location (049 R13), so every shop's timezone is the platform's
  operating timezone, Australia/Melbourne; the city in Today's subtitle follows it. A per-shop timezone is
  a later slice and the screens must read the timezone rather than assume it.
- **Currency and tax**: AUD; figures make no GST claim, because per-item GST treatment is unmodelled (052).
- **Paid means paid**: orders count once the platform has confirmed payment; `pending_payment` orders
  never appear.
- **Awaiting pick** is the same set the Orders list's Awaiting pick tab shows (057 A3).
- **Order money is shown on shop-web** (057 A3 §1.1); both roles see Insights, as both see order money.
- **Parity**: this slice is shop-web only. Shop-mobile's equivalent screens are recorded as outstanding in
  the parity register, as 057 did.
- **Deltas** use the design's wording ("+9% vs previous week", "+12% vs last Monday"); where the comparison
  window is empty the wording says so.
- **"Days of cover"** is recorded sales over the last 7 days divided into on-hand; omitted when the product
  has no recorded sales.
- **Research timing**: the research document is produced in the planning phase, before any code.
- **Not in scope** (settled, FR-011 / FR-034): product-view tracking, returns, customer messaging relays,
  shop-scoped promotions, draft or manual orders.
